まえがき

昨今のAIやそのコード生成への応用での進展は驚くべきものがあります。AnthropicがAIにCコンパイラを作らせたという報告を出したときには私も驚きましたが、私の周りでもAIが書いたコードをだいぶ見るようになってきており、驚くほどの早さで普及も進んでいます。

プログラムが自動で作れるようになってくると、次に気になるのはその「正しさ」。ソフトウェアの脆弱性は最近ではよく報道で取り上げられますが、実際、ソフトウェアの正しさを保証したり、あるいは、バグを減らすための技術はかなり以前から研究されてきたものの、なかなか世の中で広く使われる程に普及しているとは言えない状況でした。

プログラムの正しさを保証する「形式検証」と呼ばれる技術分野がありますが、これは、プログラムの「正しさ」を数学的な「証明」を与えることによって保証するものです。これがこれまで広く普及しているとは言えない状況であったのは、一言でまとめてしまえばなによりもその「数学的な証明を与えることが、プログラムを書くよりも何倍も大変」ということに尽きると思います。

ただ、これも「フェルーマーの最終定理」や「ナビエ–ストークス方程」がAI によって解かれる今なら「わりと簡単に解決できるのではないか」と、誰もが考えるでしょう。私も自分で試してみたい、とおもっていたところに、 AdaCore社のM. Anthony Aielloさんが、暗号の基本アルゴリズムにたいして、 SPARKという自社製品を適用した事例を公開 されたので、それを下敷きに同様の実験をしてみた、というのがここでの内容になります。

さて、ここでは、実際に行った実験を報告するわけですが、行った実験のほぼ全てAIによっておこなわれています。あるいはすでにご推測されていかもしれませんが、それだけでなく以降の文章のほとんどもAIが作成したものになっています。人間がおこなったのはやりたいことの指示と折々の確認への回答くらい。このような形で進めたので、技術的な内容だけでなく、以降の文章も極めて表面的なレビューはしたものの、ほぼ全てをAIが生成したものをそのまま掲載しています。(なので、そのような目でみれば日本語もややこなれない感じの日本語になっています。)

実際自分でやってみて思うのは、人間が最大のボトルネックであること。ここで作られたものを適切にレビューするには、AIがこれを生成するのに使った何倍もの時間がかかりそうです。なので、もし、何等かの理由で人間の関与が避けられない場合、例えばここで書かれた内容を人間がレビューする必要がある場合、今度はその支援をAIにしてもらうことになりそうです。

概要

2026 年 10 月 28 日、AdaCore の M. Anthony Aiello さんが、ブログ記事 Foundational Cryptography in SPARK を公開しました。NSA が公開している Cryptol の仕様集 Foundation を出発点に、AI を使って AES・SHA-256・HMAC-SHA-256 の仕様と、証明つきの実装を SPARK で作った、という内容です。機能の正しさは Platinum の水準で、仮定はひとつもありません。そのうえで、Cryptol の FFI を通したテスト、SAW による等価性の証明、MC/DC カバレッジ、ミューテーション、性能比較までをそろえています。

この記事は、その仕事を Rust と Verus で、同じ形のまま やり直した記録です。題材も、層の分け方も、証拠の積み方も SPARK 版に合わせました。SPARK 版の spark/ ディレクトリに対して、こちらは verus/ です。仕様層・実装層・補題、FFI のチェック・SAW・カバレッジ・ミューテーション・性能比較の一つひとつに、対応するものを置きました。手で書いたのは AI（Claude Code）で、人の関与は後の節に書きます。

先に結論を言うと、同じ形はほぼそのまま Verus に写せました。ただし言語と道具の違いから、SPARK 版にあって Verus 版にない証拠 が一つあります。仕様層そのものを Cryptol と突き合わせることです。逆に Verus 版で得たものもあります。これらは節ごとに対比して書きます。

SPARK 版の設計、doc、検証以外の柱の作り方がなければ、この仕事はこの短さでは終わりませんでした。Aiello さんの仕事に敬意を表します。

成果物は github.com/nobuyuki/Foundation のブランチ verus にあります。SPARK 版（spark-v1.0）の fork です。この記事の数字は、特に断らないかぎり、公開した版（d59a3f0）のものです。

NSA の Foundation

NSA の Foundation は、暗号アルゴリズムなどの仕様を Galois の Cryptol で書いて集めたリポジトリです。AES には Rust の参照実装（Cipher と KeyExpansion）も付いています。

SPARK 版はこのリポジトリに spark/ を足しただけの fork です。Verus 版もそれにならい、verus/ を足しただけにしています。NSA の既存のファイルには手を入れていません。性能比較の相手である NSA の Rust も、手を加えずに path 依存で使っています。

題材：AES・SHA-256・HMAC-SHA-256

SPARK 版と同じ 3 つです。

  • AES（FIPS 197）：鍵長 128・192・256 のすべて。鍵拡張、暗号化、復号（InvCipher と InvCipher’ の両方）
  • SHA-256（FIPS 180-4）：一括と、ストリーミング
  • HMAC-SHA-256（FIPS 198-1）：一括と、逐次

なぜこの 3 つかは、SPARK 版の記事がよく説明しています。ガロア体の算術（AES）、パディング付きの法 2^32 の語の算術（SHA-256）、ストリーミングの合成（HMAC）と、性質の違う難しさがそろっています。こちらは「同じ題材で比べたい」ので、選び直していません。進めた順は SHA-256 → HMAC → AES です。

やったこと

各アルゴリズムで、SPARK 版と同じ順に積みました。

  1. Cryptol を宣言ごとに写した 仕様層 を書く
  2. 「結果は仕様の値」を事後条件にもつ 実装層 を書く
  3. Verus で、全入力について実装が仕様に等しいこと、実行時エラーがないことを証明する
  4. Cryptol の FFI から実装を呼び、NSA の Cryptol と突き合わせて テスト する
  5. SAW で、コンパイルされた実装と NSA の Cryptol の 等価性 を固定サイズで証明する

SPARK 版との対応は次のとおりです。

Verus の仕様

仕様層は、Verus が許すかぎり Cryptol に寄せました。名前も型も、再帰や fold の形も同じです。Cryptol のビット列は Seq<bool>、語は Rust の整数です。仕様が使う Cryptol の組み込み（foldl、@、join、split、pmult、pmod など）は、src/cryptol/ に一度だけ書きました。これは SPARK 版の prelude に当たります。

ここで、SPARK 版との大きな違いが一つあります。SPARK の ghost コードはコンパイルできますが、Verus の spec fn はコンパイルされません。 SPARK 版は仕様層も実行できるので、仕様層そのものを FFI でテストし、SAW で Cryptol と等価だと証明しています。だから SPARK 版は「仕様は人が読んで確かめなくてよい」と言えます。

Verus 版にはそれができません。spec から実行コードを作る vstd の exec_spec! は、仕様層が使っているジェネリクス・trait・クロージャを受け付けないからです。そこで、仕様層が Cryptol に等しいことの根拠は次の 3 つになります。

  • 仕様と Cryptol を並べて読めること
  • Cryptol 自身が AES について述べる性質（algorithms/AES の 15 個のうち 13 個。SPARK 版と同じ）を、仕様層について全鍵長でまとめて証明したこと
  • 仕様に等しいと証明した実行コードを、FFI と SAW で Cryptol と突き合わせたこと

3 つ目は間接的で、SAW が届くのは選んだ長さだけです。この点は SPARK 版に一歩譲ります。

どのくらい「寄せた」かを、SHA-256 の例で見てみます。まず NSA の Cryptol です（algorithms/SHA2/Functions.cry と SHA256.cry）。

SIGMA_256_0 x = ROTR`{ 2} x ^ ROTR`{13} x ^ ROTR`{22} x

import algorithms::SHA2::Main as SHA256 where
  type w = 32
  SIGMA_0 = SIGMA_256_0
  ...

Verus の仕様層では、こうなります（src/sha2/functions.rs と sha256.rs）。

pub open spec fn SIGMA_256_0(x: u32) -> u32 {
    ROTR::<2, u32>(x) ^ ROTR::<13, u32>(x) ^ ROTR::<22, u32>(x)
}

impl Parameters for SHA256 {
    open spec fn w() -> nat { 32 }
    open spec fn SIGMA_0(x: u32) -> u32 { SIGMA_256_0(x) }
    ...
}

名前は Cryptol のままです（Rust の命名規則には合わないので、警告は止めています）。Cryptol のパラメータつきモジュールは trait に、そのインスタンスは trait の impl になります。

Verus の実装

実装層は、ふつうに走らせるための Rust です。ループで書き、状態をその場で書き換えます。SHA-256 と HMAC にはストリーミングの口もあります。各関数の ensures は「結果は仕様層の値」です。仕様と実装のあいだには、補題（proof fn）と表現の層を挟みます。バイト列とビット列の対応や、ストリーミングと一括の対応がそれです。

SPARK 版との違いとして、AES の鍵長は const generic（Cryptol の {k}）で持たせました。SPARK 版は実行時の引数です。

Verus の証明

  • 326 個の関数を検証、エラー 0。 冷えた状態から 16 CPU のデスクトップで約 14 秒です。Verus は検証条件ではなく関数を単位に数えるので、SPARK 版の「4,085 チェック」とは単位が違います。
  • 仮定はひとつもありません。 assume・admit・axiom fn・external_body・#[verifier::external]・停止性の免除のどれも使っていません。Verus が見ないのは、Cryptol にテスト用に公開する FFI の関数（src/ffi/）だけです。それらはすべて、理由をつけて trust-surface.txt に載せ（100 件）、スクリプトでチェックしています。
  • 全入力で、実装は仕様に等しい。 2^61 バイト未満のすべてのメッセージ長と、ストリーミングでのメッセージの切り方のすべてについて、です。
  • 重い証明はありません。 既定の resource limit を上げた関数はありません。SPARK 版で重かった S-box の証明（SBoxCorrect と SBox_Entries）に当たる Verus 版のモジュールは、単体で約 12 秒です。
  • その代わり、ソルバーへの手がかり（assert や補題の呼び出し）は、SPARK 版より多く手で書いています。

Cryptol の FFI でテストする

実装の実行コードを C の口で公開し、Cryptol から foreign で呼んで、NSA の Cryptol と :exhaust または :check で突き合わせます。性質は 73 個です。このうち 15 個は定義域が小さいので網羅し、58 個はランダムにテストします。ほかに FIPS 197・FIPS 180-4・RFC 4231 の既知の答えも確かめます。

SPARK 版の性質は 141 個です。差の 68 個は仕様層だけをテストするもので、Verus 版では spec fn を実行できないため対応するものがありません（前節）。

カバレッジ。 SPARK 版は MC/DC で 100% です。rustc には MC/DC の計装がないので、Verus 版では region・行・分岐で測りました。実装層は region 947/947、分岐 80/80 をすべて通っています。通らなかった 11 か所はすべて FFI の公開関数の中にあり、Cryptol の型がすでに保証していることを確かめるチェックでした。

ミューテーション。 SPARK 版の 84 個の 1 行の変異から、Rust のスライスで表せない 3 個を除き、SHA2.Functions の 7 個を 2 通りに書いて、88 個にしました。

  • FFI のテストが落としたのは 73 個。すり抜けた 15 個のうち 10 個は振る舞いを変えない変異で、5 個は本物のバグ でした。どれもストリーミング SHA-256 の長さの符号化にあり、テストが試すより長いメッセージ（4 KiB 以上から、最大 2^53 バイト）でしか表に出ません。SPARK 版のすり抜けの本物のバグは 6 個で、うち 1 個は Verus 版に対応するコードがありません。
  • Verus は 5 個の本物のバグをすべて弾きました。 どれも検証エラーで、時間切れではありません（SPARK 版の gnatprove は、本物のバグを時間切れで弾いています）。
  • SAW も 5 個すべてを見逃しました。SAW のハッシュの証明は 200 バイト以下の固定長だからです。これは SPARK 版と同じです。本物のバグを弾いたのは、三つのうち Verus だけでした。
  • 一方で Verus は、無害な 10 個のうち 5 個も検証に失敗しました。コードの形（xor の順番、ビットが重ならない + など）に合わせて書いた assert や不変条件が、変異のあとでは成り立たなくなるからです。証明が通らないことは、バグを見つけたことではありません。 見分けるには FFI や SAW の判定か、変異を読むことが要ります。

SPARK 版の結論「構造カバレッジの数字は、ほどほどに信じよ」は、Verus 版でもそのまま当てはまります。カバレッジは 100% でも、5 個の本物のバグがテストをすり抜けました。

SAW で等価性を証明する

SAW（Galois の Software Analysis Workbench）で、コンパイルした実装と NSA の Cryptol が等価であることを証明します。Verus の仕様は間に挟みません。対象は次のとおりで、SPARK 版と同じ範囲です。

  • AES：鍵長 128・192・256 のそれぞれで、全入力
  • SHA-256：圧縮関数は全入力、ハッシュはパディングの境目で選んだ 12 の長さ
  • HMAC：7 組の（鍵長, テキスト長）

SPARK 版は gnat-llvm の LLVM bitcode を使います。Verus 版は 2 つの経路 で同じものを証明しました。rustc が出す LLVM bitcode と、mir-json が出す MIR です。それぞれ 84 個の結果（AES 46、SHA-256 と HMAC 38）が出ます。わざと壊したコードでの対照（negative control）は各経路 8 個で、どれも期待どおり失敗しました。

SPARK 版の SAW は GNAT Pro 27 の LLVM バックエンドを要するので、公開の CI では回していません。Verus 版は、SAW まで含めてすべて無料の道具で再現できます（rustc・mir-json・Cryptol・SAW）。

一方、SPARK 版の SAW の大半は仕様層についての証明です（1,895 個のうち 1,808 個）。Verus 版には、仕様層がコンパイルされない以上、これに当たるものがありません。

全体の図

  NSA の Cryptol（algorithms/AES, SHA2, HMAC）
        ^                          ^
        | 読んで写す（＋AES の     |
        |  性質の再証明）          |
  仕様層：Verus の spec fn         | FFI のテスト（網羅・ランダム）
        ^                          | SAW（固定サイズ、LLVM bitcode と MIR）
        | Verus、全入力            | ：実装 = Cryptol
        |                          |
  実装層：Rust（ensures：結果は仕様の値）

SPARK 版の図にあって、この図にない矢印が一本あります。「仕様層 → Cryptol」を機械で結ぶ矢印（仕様層の FFI テストと SAW）です。

性能

証明を手に入れる

SPARK 版は、エージェントが証明を緑にするまでにかかった時間を、層ごとに会話の記録から集計しています。同じ定義で数えました。各セッションの延べ時間から 30 分を超える空白を引き、道具の待ち時間は道具の種類ごとにコマンドが動いていた区間の和集合とします。残りがエージェント自身の作業です。

違いが一つあります。SPARK 版の作業は、オーケストレーターが下請けのエージェントに任せる自律型でした。こちらは人との対話型で、下請けは使っていません。そのため、人の返事待ち（人のプロンプトの直前の空白）を別の列に分けました。

単位は時間です。2026-11-01 の夕方に始め、この 5 層は同じ日の夜（約 5 時間後）に終わりました。

SPARK 版の対応する 5 層の合計は 17.08 時間です。SPARK 版にはさらに、仕様層の SAW（14.22 時間）と、レビューの後に仕様を直して証明し直す層（12.26 時間と 8.19 時間）があり、総計は 51.75 時間です。Verus 版にはこの 3 層がありません。仕様層の SAW はできず、仕様を作り直すレビューのやり直しもなかったからです。

この比は、AI や道具の優劣を言うものではありません。 いちばん大きな違いは、こちらには SPARK 版という完成した手本があったことです。何を作るか、どう層を分けるか、どの性質を試すか、どのサイズで SAW を回すかは、すべて SPARK 版に書いてありました。SPARK 版は、それを最初から決めています。そのうえで、道具の速さの違いもあります。Verus の 1 回の検証は秒の単位で、gnatprove の分の単位とは違います。SPARK 版で重かった SBoxCorrect の再証明（1 回約 20 分）も、こちらでは約 12 秒でした。モデルはどちらも同じです。

ここに入れていない作業もあります。カバレッジ、ミューテーション、性能比較、doc、道具の導入と trust surface です。SPARK 版の記事もこれらは表に入れていません。

人の関与

(注：「人の関与」という節なので、本節はAIでなく人が半分くらい書いています。というか、人が書け、とAIに言われたので、AIの下書きをもとに人間が手を入れています。)

SPARK 版の記事は、仕様・実装・証明・テストを人の手引きなしで作り、人は AES の仕様をレビューして書き方を提案しただけ、としています。

こちらも、コード・証明・スクリプト・doc を書いたのはすべて AI です。人が決めたのは次のことでした。

  • 目標：SPARK 版と同じ形で、同じ証明の水準（仮定なし）で、検証以外の柱も含めてやること
  • 進める順番と区切り（SHA-256 → HMAC → AES → 検証以外の柱 → doc）
  • AI が出した判断の了承。たとえば、MC/DC がないことを受け入れて「MC/DC なし」と明記する、ミューテーションの番号を SPARK 版と対応がつく形にする、など
  • 道具の導入の許可と、マシンを専有するミューテーションの夜間実行
  • 公開の範囲

本来であれば、AIが生成した仕様付きのRust(Verus)コードを、NSAによる Crypto/SAWによる記述や、AdaCoreのM. Anthony AielloさんのSPARK記述と仔細に比較、検討するというのが、AIによって浮いた時間の正しい使い方⋯ではあるのですが⋯。

再現の方法

verus/README.md と verus/doc/reproducing.md に手順があります。必要なのは Verus（版は Cargo.toml に固定）、Rust 1.98.1、Cryptol 3.6.0、SAW 1.6、mir-json で、どれも無料です。

$ cd verus
$ cargo build && cargo test
$ cargo verus verify                    # 326 verified, 0 errors
$ scripts/check-trust-surface.sh
$ scripts/check-ffi.sh                  # Cryptol 3.6.0（FFI つき）が要る
$ scripts/check-saw.sh                  # SAW 1.6 と mir-json が要る

まとめ

  • SPARK 版の形は、Verus にほぼそのまま写せました。仕様層・実装層・補題の 3 層、仮定のない全入力の証明、FFI・SAW・カバレッジ・ミューテーション・性能比較のすべてに対応物があります。
  • 写せなかったのは、仕様層を実行して Cryptol と突き合わせることです。Verus の spec fn はコンパイルされません。仕様層の正しさは、読むこと、性質の再証明、実装を通した間接的な突き合わせに頼ります。
  • 得たものもありました。証明は数秒で回り、遅い証明がありません。SAW を含むすべての道具が無料です。SAW を 2 つの経路で通しました。同じ rustc 同士の性能比較で、約 2 倍の速さが出ました。
  • ミューテーションは SPARK 版と同じ教訓を繰り返しました。カバレッジは 100% でもテストは本物のバグを見逃し、それを弾いたのは証明だけでした。一方で、証明の失敗はバグの発見とは限りません。
  • 手本があれば、AI による移植は速い。この仕事の速さの大半は、SPARK 版が先に道を切り開いていたことによります。

注意書き

SPARK 版と同じく、セキュリティが問題になる場面でこのコードを使わないでください。 証明したのは機能の正しさだけです。サイドチャネルなど機能以外の性質は扱っていません。特に、この AES は定数時間ではありません。S-box は鍵と状態のバイトを添字にした表引きです。

コンパイラ（rustc、mir-json）、Verus 自身・vstd・SMT ソルバーは信頼しています。証明していません。

FAQ

Verus とは？

Rust のための検証器です。Rust のコードに requires・ensures・ループ不変条件・補題を書き、SMT ソルバー（Z3）で証明します。証明のためのコード（spec・proof・ghost）は、通常のビルドでは消えます。Carnegie Mellon 大学と Microsoft Research を中心に、MPI-SWS、VMware Research、ETH Zurich などの研究者が開発しているオープンソースの道具です（verus-lang/verus）。論文は OOPSLA 2023 と SOSP 2024 にあります。

Verus は何に使われている？

主にシステムソフトウェアの検証です。たとえば次のものがあります。

  • SOSP 2024 の論文での評価：分散システム、OS のページテーブル、NUMA 向けの並行データ構造、メモリアロケータ
  • VeriSMo：AMD SEV-SNP の機密 VM のためのセキュリティモジュール（OSDI 2024 Best Paper）
  • Anvil：Kubernetes のコントローラの検証（OSDI 2024 Best Paper）
  • Atmosphere：Rust と Verus で書いた検証済みのマイクロカーネル（SOSP 2025）

AI が書いた Verus のコードが正しいと、なぜ言えるのか？

AI を信じているからではありません。互いに独立した次の証拠によります。

  1. Verus による、全入力での「実装 = 仕様」と実行時エラーの不在の証明（仮定なし。仮定の不在はスクリプトでチェック）
  2. SAW による、コンパイルされた実装と NSA の Cryptol の等価性の証明（AES は全入力、SHA-256 と HMAC は選んだ長さ。2 経路）
  3. Cryptol の FFI を通した、NSA の Cryptol との突き合わせテスト（網羅とランダム。実装層はカバレッジ 100%）
  4. ミューテーションによる、上の 3 つの効き目の確認

SPARK 版の 4 本の柱のうち「仕様層と Cryptol の等価性の機械による確認」は、Verus 版では 2 と 3 を通した間接的なものになります。
